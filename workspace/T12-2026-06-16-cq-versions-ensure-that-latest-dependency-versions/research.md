# Research Findings

## Q1: How and where are dependencies declared in `pyproject.toml`, and what version constraints apply?

### Findings
- **Runtime dependencies**: `dependencies = []` — empty list (`pyproject.toml:18`). The package has no runtime dependencies.
- **Optional/extra group** `test` (`pyproject.toml:27-38`): `hatch`, `ruff`, `mypy`, `pip-audit`, `deadcode`, `pytest`, `pytest-cov`, `pytest-xdist`, and `vupi>=0.0.6`.
- **Version constraints**: only `vupi>=0.0.6` carries a constraint (`pyproject.toml:37`). All other entries in the `test` extra are unpinned (no version specifier).
- **Build-system requirements** (`pyproject.toml:46-48`): `requires = ["hatchling"]` (unpinned), `build-backend = "hatchling.build"`.
- There is a single extra group named `test`; there is no separately-declared `dev` group in `[project.optional-dependencies]` (`pyproject.toml:27`).
- Tool configs co-located in the same file: ruff (`:57-80`), mypy (`:82-90`), pytest (`:40-44`), deadcode (`:92-96`), hatch build/version (`:50-55`).
- `uv.lock` confirms the declared metadata: `requires-dist` lists the 9 test-extra packages, only `vupi` has `specifier = ">=0.0.6"` (`uv.lock:733-743`), `provides-extras = ["test"]` (`uv.lock:744`).

## Q2: How are `uv.lock`, `requirements.txt`, and `requirements-dev.txt` generated and kept consistent?

### Findings
- **`requirements.txt` / `requirements-dev.txt`** are generated by the `make compile` target (`Makefile:53-55`):
  - `uv pip compile -U -q pyproject.toml -o requirements.txt`
  - `uv pip compile -U -q --all-extras pyproject.toml -o requirements-dev.txt`
  - The `-U` flag upgrades to latest versions; `--all-extras` pulls the `test` extra into the dev file.
- File headers confirm generation: `requirements.txt:1-2` (`uv pip compile pyproject.toml -o requirements.txt`) and `requirements-dev.txt:1-2` (`uv pip compile --all-extras pyproject.toml -o requirements-dev.txt`).
- `requirements.txt` is effectively empty (header only) because runtime `dependencies = []` (`requirements.txt:1-2`).
- `requirements-dev.txt` contains fully-pinned transitive closure (~278 lines, e.g. `ruff==0.15.17` at `:225`, `vupi==0.0.7` at `:279`, `mypy==2.1.0` at `:126`).
- **`uv.lock`**: a uv-native lock file (`version = 1`, `revision = 3`, `uv.lock:1-2`) containing 102 packages (`grep -c '[[package]]'`). It is not produced by `make compile`; it is maintained by uv's own resolver (e.g. `uv sync`/`uv lock`). The Makefile/Justfile do not have an explicit recipe that runs `uv lock`.
- There is no recipe that re-generates `uv.lock` from `pyproject.toml` explicitly; the `Makefile lifecycle` target runs `uv sync --group dev` (`Makefile:7`) which would touch the lock, but no `dev` group is declared in `pyproject.toml` (Q1) — note this mismatch.
- README documents the intended flow: `make compile` "bump and freeze dependency versions in requirements*.txt files" then `make sync` "upgrade installed dependencies" (`README.md:20-21`).

## Q3: How are dependencies installed/synchronized for local dev and CI, and which index sources?

### Findings
- **Local dev (Makefile)**:
  - `.venv` target (`Makefile:13-20`): installs uv if missing, `uv venv -p 3.14`, then `uv pip sync requirements-dev.txt` and `uv pip install -e .[test]`.
  - `sync` target (`Makefile:49-51`): `uv pip sync requirements-dev.txt` + `uv pip install -e .[test]`.
  - Most targets depend on `.venv` and call tools via `.venv/bin/<tool>` (`Makefile:27-47`).
- **Local dev (Justfile)**:
  - `sync` recipe (`Justfile:6-8`): `uv pip sync requirements-dev.txt` + `uv pip install -e .[test]`.
  - Every task recipe (`test`, `format`, `lint`, `typecheck`, `check-*`) declares `: sync` as a prerequisite and runs tools via `uv run <tool>` (`Justfile:10-37`).
- **CI (`.gitlab-ci.yml`)**:
  - `image: python:latest` (`:1`).
  - `before_script: make .venv` (`:13-14`) — builds the venv from `requirements-dev.txt` + extras.
  - single `test` job runs `make check` (`:16-18`).
  - pip cache directed to `.cache/pip`; `RUFF_CACHE_DIR` set inside project (`:5-11`).
- **Package index sources**:
  - A private GitLab uv index is configured: `[[tool.uv.index]]` name `gitlab`, url `https://gitlab.com/api/v4/projects/niekas%2Fpackages/packages/pypi/simple` (`pyproject.toml:98-100`).
  - `uv.lock` resolves every package's `source` to that GitLab registry (the only registry source present; the other source is `editable = "."` for the project itself) — verified via `grep -o 'source = {...}'` (two distinct sources only).
  - Wheel/sdist download URLs in the lock still point at `files.pythonhosted.org` (e.g. `uv.lock:13-15`).

## Q4: What dependency auditing/validation tooling exists, and when is it invoked relative to `check`?

### Findings
- **pip-audit** (vulnerability scanning) and **deadcode** (unused-code detection) are both in the `test` extra (`pyproject.toml:31,33`).
- **Makefile**:
  - `audit` target (`Makefile:40-41`): `.venv/bin/pip-audit --skip-editable`.
  - `deadcode` target (`Makefile:43-44`): `.venv/bin/deadcode modernpackage tests`.
  - `check` aggregates them: `check: test lint mypy audit deadcode` (`Makefile:10`) — audit and deadcode run as part of the combined gate.
  - `fixlint` (`Makefile:30-32`) also runs `deadcode --fix`.
- **Justfile**:
  - The Justfile `check` is `check-format check-lint check-complexity check-typecheck test` (`Justfile:37`) — it does **not** include pip-audit or deadcode. So audit/deadcode are only in the Makefile `check`, not the Justfile `check`.
- **pip-audit config**: none in `pyproject.toml`; invoked with `--skip-editable` only (so the editable project itself is skipped) (`Makefile:41`; confirmed `docs/specification.md:90`).
- **deadcode config** (`pyproject.toml:92-96`): `ignore_names = ["main"]`, `exclude = ["tests"]`.
- **CI** invokes `make check` (`.gitlab-ci.yml:18`), so audit + deadcode run in CI via the Makefile path.

## Q5: How is the required Python version specified, and how does it interact with resolution/lock markers?

### Findings
- **`pyproject.toml`**: `requires-python = ">= 3.14"` (`:8`); classifier `Programming Language :: Python :: 3.14` (`:15`).
- **mypy**: `python_version = "3.14"` (`pyproject.toml:84`).
- **Makefile `.venv`**: creates the env with `uv venv -p 3.14` (`Makefile:18`).
- **`uv.lock`**: `requires-python = ">=3.14"` (`uv.lock:3`), and `resolution-markers` split on `python_full_version >= '3.15'` and `< '3.15'` (`uv.lock:4-7`) — uv resolves two marker branches around the 3.15 boundary.
- Lock wheels target cp314 (e.g. `ast-serialize` cp314/cp314t wheels, `uv.lock:32-...`), consistent with the 3.14 floor.
- BACKLOG records `[T11] [cq:python] Ensure that latest stable python version is used` as done (`[x]`) (`BACKLOG.md:31`).

## Cross-Cutting Observations
- **Two parallel build/task systems**: `Makefile` and `Justfile` overlap but diverge. Makefile `check` includes `audit` + `deadcode` (`Makefile:10`); Justfile `check` omits both (`Justfile:37`). CI uses the Makefile (`make check`, `.gitlab-ci.yml:18`). Merging them is a noted backlog item (`docs/overview.md:66`).
- **Three dependency artifacts coexist**: `uv.lock` (uv-native, 102 pkgs), `requirements.txt` (empty/runtime), `requirements-dev.txt` (pinned dev closure). `make compile` only regenerates the two requirements files; the lock is maintained separately by uv.
- **Pinning philosophy**: declarations are mostly unpinned (only `vupi>=0.0.6`), with concrete pins frozen into `requirements-dev.txt` via `uv pip compile -U` and into `uv.lock`.
- **Single private index** (GitLab) is the resolution source for all locked packages (`pyproject.toml:98-100`; `uv.lock` sources).
- Task context: `[T12] [cq:versions]` is in-progress (`[~]`) in BACKLOG (`BACKLOG.md:32`); `cq:versions` = "Dependency version updates" (`docs/backlog_formats.md:35`).

## Open Areas
- **`uv.lock` regeneration recipe**: no explicit `uv lock` recipe exists in Justfile/Makefile. `Makefile lifecycle` calls `uv sync --group dev` (`Makefile:7`), but `pyproject.toml` declares no `dev` dependency group (only the `test` extra) — the mechanism that keeps `uv.lock` current is not encoded in a named recipe.
- Whether `make compile` and `make sync` are expected to keep `uv.lock` in sync is not documented; README/spec describe them only in terms of `requirements*.txt` (`README.md:20-21`, `docs/specification.md:78`).
