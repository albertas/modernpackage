# Research Findings

## Q1: How are tests structured, and what mocking/patching techniques do they use?

### Findings
- The entire suite is a single file: `tests/test_main.py` (8 tests). `tests/__init__.py:1` is empty; there is **no `conftest.py`** and no fixtures defined anywhere.
- Tests are top-level `def test_*` functions returning `-> None`; no test classes, plain `assert` (`tests/test_main.py:10`, `:20`, `:24`, ...). Matches the project convention in `Code Best Practices`.
- Mocking is exclusively `unittest.mock.patch` used as **context managers** (`from unittest.mock import patch`, `tests/test_main.py:2`):
  - Patching the seam by string path on the defining module, e.g. `patch('modernpackage.main.ArgumentParser')` (`:12`, `:49`), `patch('modernpackage.main.print')` (`:13`, `:60`), `patch('modernpackage.main.Popen')` (`:42`), `patch('modernpackage.main.init_new_package')` (`:50`, `:62`).
  - Patching `sys.argv` to drive arg parsing: `patch('sys.argv', [...])` (`:30`, `:36`).
  - Multiple patches combined via parenthesized `with (...)` blocks (`:11-14`, `:48-51`, `:58-63`).
- Assertions use mock methods: `assert_called_once_with` (`:17`, `:55`), `assert_not_called` (`:67`, `:68`), and `popen_mock.called` (`:44`).
- Exception testing uses `pytest.raises(ArgumentTypeError, match=...)` (`tests/test_main.py:25`); `import pytest` at `:4`.

## Q2: Which `modernpackage/` code paths do external interactions, and how are they exercised?

### Findings
- All external interaction lives in `modernpackage/main.py`; `modernpackage/__init__.py` only defines `__version__` (`__init__.py:3`).
- `init_new_package(package_name)` (`main.py:37-51`) is the only external-effect path:
  - **Network + subprocess**: `Popen(['git', 'clone', 'https://github.com/albertas/modernpackage', new_package_path], ...)` then `pipe.communicate()` (`main.py:41-46`).
  - **Subprocess + filesystem**: `Popen(['make', 'init', package_name], ..., cwd=new_package_path)` then `communicate()` with output decode/split (`main.py:48-51`).
  - **Filesystem**: `Path.cwd() / package_name` (`main.py:39`).
- How exercised by tests: `test_init_new_package` patches `modernpackage.main.Popen` and only asserts `popen_mock.called` (`tests/test_main.py:41-44`). The real `git clone` / `make init` are **never executed** because `Popen` is mocked; no network or disk is touched.
- `print` side effect (`main.py:59`) is mocked in `test_show_version` and `test_main_no_args` (`tests/test_main.py:13`, `:60`).
- Pure/no-external functions: `check_alpha_numeric` (`main.py:10-15`) tested directly without mocks (`tests/test_main.py:20-26`); `parse_args` (`main.py:18-34`) tested by patching `sys.argv`.

## Q3: How is the test runner configured and invoked (Justfile, pyproject, CI)?

### Findings
- **Justfile** (`Justfile:10-11`): `test *args: sync` → `uv run pytest {{args}}`. The `sync` dep (`Justfile:6-8`) runs `uv pip sync requirements-dev.txt` + `uv pip install -e .[test]`. `check` aggregates `check-format check-lint check-complexity check-typecheck test` (`Justfile:34`).
- **Makefile** (`Makefile:46-47`): `test: .venv` → `.venv/bin/pytest $(TEST_NAME)`. `check: test lint mypy audit deadcode` (`Makefile:10`).
- **pyproject `[tool.pytest.ini_options]`** (`pyproject.toml:39-40`): `addopts = "--cov=modernpackage --no-cov-on-fail --cov-fail-under=95.0"`. This is the only pytest config; no `testpaths`, no `markers`, no parallelism options.
- **Coverage**: enforced at 95% via `--cov-fail-under=95.0` (`pyproject.toml:40`); a `.coverage` file is present at repo root. `pytest-cov`/`coverage` are installed (`requirements-dev.txt:39`, `:191`).
- **CI — GitLab** (`.gitlab-ci.yml`): `before_script: make .venv` (`:13-14`), `test:` job runs `make check` (`:16-18`), image `python:latest` (`:1`).
- **CI — GitHub** (`.github/workflows/check-modernpackage-on-python311.yml`): on push/PR to `main`; sets up Python 3.14 (`:22-25`), `make .venv` (`:27-28`), then `make check` (`:30-31`).
- **Parallelism / core counts**: none configured anywhere currently — no `-n`, no `--numprocesses`, no `nproc` in any Justfile/Makefile/pyproject/CI recipe (confirmed by grep). pytest runs single-process.

- **pytest-xdist: NOT present.** No `pytest-xdist` (nor any parallel-execution plugin like `pytest-parallel`/`pytest-forked`) appears in `pyproject.toml`, `requirements-dev.txt`, or `uv.lock` (grep returned no matches). The only pytest plugin installed is `pytest-cov`.

## Q5: Conventions for selecting CPU core counts (e.g. `nproc`-based expressions)?

### Findings
- **No `nproc` usage in modernpackage's own runnable files** (Justfile/Makefile/pyproject) currently.
- The convention is documented as an example in `BACKLOG.md:8`: the referenced sibling-project Justfile style uses
  `uv run pytest -n "$(nproc --ignore=1)" {{args}}` (i.e. xdist with all cores minus one).
- The same convention is embedded in the **vupi sibling package** source: `.venv/.../vupi/_code_quality.py:49` contains the literal recipe `uv run pytest -n "$(nproc --ignore=1)" {{args}}`.
- `nproc --ignore=1` = "all available cores minus one" — the "max − 1 cores" pattern. No `cpu_count`/`os.cpu_count` based selection exists in the project's recipes.

## Q6: Existing end-to-end / integration tests vs unit tests; how marked/grouped/selected?

### Findings
- **No e2e or integration tests exist.** All 8 tests in `tests/test_main.py` are unit tests that mock external effects (`Popen`, `print`, `ArgumentParser`, `sys.argv`).
- **No pytest markers** are defined or used: no `markers` entry in `[tool.pytest.ini_options]` (`pyproject.toml:39-40`), no `@pytest.mark.*` decorators in the test file, no `-m` selection in any Justfile/Makefile recipe.
- **No grouping mechanism**: a single test file, no test subdirectories (`tests/` contains only `__init__.py` and `test_main.py`), no naming convention separating fast/slow or unit/e2e.
- Test selection is only positional: Justfile `test *args` passes through to pytest (`Justfile:10-11`); Makefile uses `$(TEST_NAME)` (`Makefile:47`).

## Cross-Cutting Observations
- Two parallel task runners coexist: `Justfile` (uv-run based) and `Makefile` (`.venv/bin`-based); CI uses the Makefile (`make check`) while local convention favors the Justfile. `BACKLOG.md:34` notes intent to merge Makefile into Justfile.
- The project mirrors conventions from the `vupi` sibling/tooling (CLAUDE.md references `app/vupi/`; vupi is a `[test]` dependency, `pyproject.toml:36`). Code-style rules (single quotes, full-word names, patch-the-seam testing) are consistent between this repo's tests and the stated conventions.
- Determinism today rests entirely on mocking: no test touches network, subprocess, or filesystem because every effectful seam (`Popen`, `Path.cwd` via mocked `Popen`, `print`) is patched.
- Python target is 3.14 (`pyproject.toml:6`, `:78`); CI workflow filename says `python311` but actually installs 3.14 (`.github/workflows/check-modernpackage-on-python311.yml:22-25`).
